

== Frequency and time analysis

ASysC combines circuit description with symbolic transformation. A netlist can
be interpreted in different ways depending on the analysis mode: the same basic
circuit may be expanded into frequency-domain equations or into time-domain
equations for transient simulation. The structure of the circuit remains the
same; only the equation set used for evaluation changes.

To run all example simulations from the repository root:

[source, console]
----
make run
----

This builds any out-of-date example models, runs each `simulation.py`, and
displays its plots. The examples below explain the two main analysis modes
that the project supports: frequency-domain AC analysis and transient time-domain
analysis.

=== Frequency analysis

Frequency-domain analysis, commonly called AC analysis, is selected with
`SOLVE_AC()`:

    CIRCUIT := SOLVE_AC( RLC )

This directive tells the compiler to transform the circuit into a form suitable
for sweeping frequency. The transformation is applied before the circuit
equations are derived, and the resulting model is conventionally assigned to
`CIRCUIT`, which is the symbol the compiler uses as the top-level model by
default.

The purpose of this stage is to describe how the circuit responds across a range
of frequencies, rather than how it behaves at a single instant in time. In
engineering terms, this is the right tool for studying gain, phase, filtering,
and frequency-selective behavior.

NOTE: Automatic DC bias-point calculation is not implemented. Provide
appropriate source and initial values for the analysis being modeled.

==== Example with a conventional *R, L, C* circuit

A simple RLC network is a useful place to begin because it exercises the core
idea of frequency-based circuit modeling without introducing additional
nonlinear behavior. In this example, the circuit includes a voltage source
(`CV`), a resistor (`CR`), an inductor (`CL`), and a capacitor (`CC`). The
instances are named `V`, `R`, `L`, and `C`, and the nodes are labeled `@1`
through `@4`.

image::circuit_RLC.png[align="center", scale=50%]

The netlist description of this circuit is:

----
`include <components.rule>

RLC() := {
    V.CV(@1, @2, 1);
    R.CR(@2, @3, 100);
    L.CL(@3, @4, 1m);
    C.CC(@4, @1, 10u)
};

CIRCUIT := SOLVE_AC( RLC )
----

The component instances form the body of the `RLC()` rule. Once the circuit is
assembled, `SOLVE_AC()` derives the frequency-domain model from that topology.
The result is a symbolic description of the network as a function of frequency,
which is then evaluated by the generated Python code.

The `+`include+` directive loads component definitions that are not part of the
default rule set. You can define additional components in your own `.rule`
file and include it in the netlist.

==== Generating _Python_ code

Once the circuit definition is ready, compiling the netlist from the repository
root produces a Python model:

[source, console]
----
./bin/asysc -i examples/ac/RLC_slider/RLC.cir \
  -o examples/ac/RLC_slider/RLC.py -t ac
----

The generated file is not meant to be hand-edited. It contains the circuit
equations and stores the computed values in each element's history, which is
precisely the information used by the plotting code. In other words, the
netlist is the source of truth; the generated Python file is a build artifact.

To run the frequency simulation, create a circuit object in `simulation.py`
and call `simulate_f(start, end, samples)`. The frequency points are distributed
logarithmically between the start and end frequencies, which is useful for
visualizing wide-band responses without over-sampling the lower end.

[source, python]
----
model = circuit()
model.simulate_f(10, 1e6, 100)
----

For the checked-in RLC slider example, generate the model and then run the
simulation script from the example directory:

[source, console]
----
cd examples/ac/RLC_slider
python3 simulation.py
----

The model's element histories contain the computed data. The example uses NumPy
and Matplotlib to display the frequency response, so each sweep can be inspected
both numerically and visually:

image::RLC_ac.png[align="center", scale=50%]

==== Frequency analysis with dynamic change of parameter values

One of the practical strengths of ASysC is that circuit parameters can be read
from Python-side variables. This makes it possible to change values between
simulation runs without recompiling the netlist. In a design workflow, that
means the same circuit can be reused in a parameter sweep or interactive tuning
session with minimal effort.

The `_getv()` rule reads the current value of a Python-side model variable.
The RLC slider circuit uses it as follows:

----
`include <components.rule>

RLC( PR, PL, PC ) := {

    V.CV (@1, @2, 1);
    R1.CR(@2, @3, PR );
    L1.CL(@3, @4, PL );
    C1.CC(@4, @1, PC )
};

CIRCUIT := SOLVE_AC( RLC( _getv( R ), _getv( L ), _getv( C ) ) )
----

The circuit accepts resistance, inductance, and capacitance as parameters.
During simulation, `_getv()` retrieves the values stored on the generated Python
model, allowing sliders or other UI controls to modify the component values live.
This keeps the circuit representation compact while preserving a convenient path
for interactive parameter exploration.

The `examples/ac/RLC_slider/simulation.py` script demonstrates interactive
sliders for these parameters.

The simulation results window featuring sliders:

image::ac_slider.png[align="center", scale=50%]

==== Another circuit example: a *Sallen-Key* type filter

The next example demonstrates a second-order Sallen-Key filter <<R9>>, a classic
active filter structure built from RC sections and an operational amplifier.
This case is useful because it exercises both passive and active behavior in the
same netlist, while also showing how the generated results can be displayed as a
gain and phase plot.

The circuit description:

----
`include <components.rule>

sallen_key() :=
{
	V.VSIN   ( @1, @0, 1 );		
	R1.CR    ( @1, @2, 100 );
	R2.CR    ( @2, @3, 100 );
	C1.CC    ( @2, @4, 820p );
	C2.CC    ( @3, @0, 390p );
	A.IOPAMP ( @3, @4, @4, @0 )
};

CIRCUIT := SOLVE_AC( sallen_key )
----

== Time analysis, also known as "Transient Analysis"

Transient analysis is the time-domain counterpart to AC analysis. It is selected
with `SOLVE_TRANS()`:

    CIRCUIT := SOLVE_TRANS( RLC )

This directive tells the compiler to generate equations that evolve with time,
which is essential when the circuit contains reactive elements or nonlinear
switching behavior. The solver then advances the system through a sequence of
steps, tracking how currents and voltages evolve as the signal changes.

This form of analysis is especially important when studying pulses, switching,
rectification, startup behavior, and the build-up of charge on capacitors.

The nonlinear equations are handled with an iterative linearization based on
the Newton-Raphson method <<R10>>. At each iteration, the equations are
linearized around the current estimate, solved, and updated until the
iteration limit or convergence condition is reached.

Reactive elements such as capacitors and inductors use trapezoidal
integration, a standard method for capturing the time-varying behavior of energy
storage elements while retaining numerical stability over a step sequence.

=== Example of a Graetz bridge simulation in transient analysis

The Graetz bridge is a classic rectifier circuit: it converts an AC source into a
pulsating DC output using four diodes and a load. In this example, the circuit
contains a sinusoidal source `V`, source resistor `R2`, four diodes, and a load
made of resistor `R1` and capacitor `C`.

----
`include <components.rule>

graetz_bridge( RS ) :=
{
    V.VSIN   ( @5, @3, 10, 2*PI*600 );
    R2.CR    ( @5, @2, 1 );
    D1.DIODE ( @1, @2 );
    D2.DIODE ( @1, @3 );
    D3.DIODE ( @2, @4 );
    D4.DIODE ( @3, @4 );
    R1.CR    ( @1, @4, RS );
    C.CC     ( @1, @4, 1u )
};

CIRCUIT := SOLVE_TRANS( graetz_bridge( 500 ) )
----

The corresponding schematic and simulation result:

image::graetz_bridge.png[align="center"]

The generated model is run from `simulation.py` by calling
`simulate_t(duration, nb, res, max_iter)`. Here, `duration` is the total
simulated time, `nb` is the number of time steps, `res` controls the iterative
update and convergence check, and `max_iter` limits iterations per step.

[source, python]
----
model = circuit()
model.simulate_t(duration=1e-3, nb=500, res=0.1, max_iter=100)
----

Before simulating, it is often useful to initialize a model variable by calling
`init()` on its element. The `transient/oscillator` example does exactly that to
set an initial logic level before the transient begins:

[source, python]
----
model.NOT1_Uin.init(5)
----

=== Example: diode RC envelope detector

The
link:../examples/transient/envelope_detector/envelope_detector.cir[envelope
detector netlist] drives a diode and a 100 kΩ / 100 nF RC load with a 1 kHz
sinusoid. The load's time constant is 10 ms, which is long enough for the
capacitor to charge near the input peaks and discharge between them. This is the
basic principle behind envelope detection: the output follows the peaks of the
input signal while smoothing the high-frequency ripple.

The generated model exposes both input and output probes. The simulation script
plots them over a 20 ms transient so that the charging and discharging waveform is
easy to compare with the original signal.

Run the example after building its model:

[source, console]
----
make -C examples
cd examples/transient/envelope_detector
python3 simulation.py
----

== Compact modeling

The NE555 timer is a particularly instructive example of compact behavioral
modeling. In a full transistor-level description, the internal structure of the
chip would be large and cumbersome. A compact model instead captures the
behavior that matters to the surrounding circuit: the control thresholds,
timing relationships, and switching behavior that determine the oscillation.

This is a common engineering strategy. Rather than trying to reproduce every
internal detail, a compact model focuses on the externally observable
relationships that matter for circuit-level simulation. The result is a smaller,
more readable description that can still be used to reason about system behavior.

As an example, the *NE555*'s compact behavioral description includes just two
subcomponents:

- a *SWITCH* component
- a *SRFFC* set-reset type flip-flop

plus a few logic equations. It all fits into just a few lines, as illustrated in
the netlist below:

----
NAME.NE555( @trigger, @threshold, @discharge, @output, @vcc, @gnd ) :=
{
    NAME.VCC    = ACROSS( @vcc, @gnd );
    NAME.UTRIG  = ACROSS( @trigger, @gnd );
    NAME.UTRESH = ACROSS( @threshold, @gnd );
    NAME.UOUT   = ACROSS( @output, @gnd );
    NAME.UIN1   = ACROSS( NAME.@in1, @gnd );
    NAME.UIN2   = ACROSS( NAME.@in2, @gnd );

    NAME.UIN1 = ( NAME.UTRIG < ( NAME.VCC / 3 ) );
    NAME.UIN2 = ( NAME.UTRESH < ( NAME.VCC * 2 / 3 ) );

    NAME.SW.SWITCH( @discharge, @gnd, NAME.UOUT < (NAME.VCC/2) );
    NAME.SR.SRFFC( NAME.@in1, NAME.@in2, @output, @vcc, @gnd)
};
----

The logic is intentionally simple and expressive: the trigger and threshold
signals are compared against fractions of the supply voltage, and the flip-flop
state is updated according to those conditions. This is a compact but faithful
representation of the circuit's control logic.

The following test circuit uses the model. The `include` directives load the
analog components and integrated-circuit definitions it needs:

----
`include <components.rule>
`include <ic.rule>

test_NE555( R ) :=
{

  V1.CV     ( @3, @0, 7.5 );
  C1.CC     ( @1, @0, 1u );
  RB.CR     ( @2, @1, R);
  RA.CR     ( @3, @2, 2.7K );
  U.NE555   ( @1, @1, @2, @4, @3, @0  );
  P1.UPROBE ( @4, @0 );
  P2.UPROBE ( @2, @0 )
};

CIRCUIT := SOLVE_TRANS( test_NE555( _getv( _RV ) ) )
----

The compact model's internal nodes `NAME.@in1` and `NAME.@in2` are namespaced by
the instance name. For instance, `U` leads to internal nodes `U.@in1` and
`U.@in2`, so they do not conflict with external circuit nodes. This is one of
those small but important implementation details that makes hierarchical models
manageable.

Below is the result of a simulation with the *NE555* in an oscillator
configuration:

image::ne555.png[align="center"]

This compact description provides a simpler model for system-level simulation;
it is not intended to replace the detailed physical structure of the device, but
rather to retain the behavior that matters. Its accuracy depends on the
assumptions encoded in the equations, which is often exactly what is desired in
early-stage modeling or subsystem exploration.

The circuit shown in the example above contains probes *P1* and *P2*. These are
used to visualize the voltages between two given nodes.

- `P1` measures the NE555 output relative to ground.
- `P2` measures the discharge node relative to ground.

Probes make selected internal and external voltages available to the generated
Python model, which makes debugging and interpretation of the behavior much more
straightforward.
