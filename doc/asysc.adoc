

== ASysC, the Analog System Compiler

_ASysC_ is a symbolic front end for analog modeling and simulation. The basic
idea is to express a circuit as a set of symbolic equations, apply rewriting
rules to simplify or transform them, and then compile the result into Python
code that evaluates the model numerically. This differs from a traditional
simulator that repeatedly assembles and solves a matrix at each evaluation point.

In ASysC, the symbolic structure remains visible. The user can see how circuit
relationships are derived, simplified, and combined before the numerical
simulation runs.

=== How does a CAS work?

A computer algebra system stores mathematical expressions as trees. Consider the
expression stem:[-(a-b)]: internally, it is represented by a nested structure in
which the top-level operator is a unary minus applied to a subtraction. This
kind of representation is very different from a plain string or a floating-point
number; it preserves the structure of the expression and makes symbolic
transformation possible.

[.text-center]
[mermaid, format=png, align="center"]
....
---

  theme: neutral
  look: neo
---
flowchart TB
    subgraph a [ ]
    direction TB
    A((−)) --> B((−))
    B --> C((a))
    B --> D((b))
    end
....

A CAS contains rules that transform these expression trees. For example, there is
an algebraic simplification rule that turns the expression stem:[-(a-b)] into
stem:[b-a]. In ASysC, this is conceptually written as:

stem:[-(a-b)] := stem:[(b-a)]

The rule matches a subexpression of the appropriate shape and replaces it with
an equivalent but simpler tree:

[.text-center]
[mermaid, format=png, align="center"]
....
---
config:
  theme: neutral
  look: neo
---
flowchart LR
    subgraph a [ ]
        direction TB
        A((−)) --> B((−))
        B --> C((a))
        B --> D((b))
    end
    subgraph b [ ]
        direction TB
        E((−))
        E --> F((b))
        E --> G((a))
    end
    a --"Simplification"--> b
....

Parameters **a** and **b** can themselves be numbers, variables, or larger
expressions. This means the rule engine deals naturally with nested structures,
not just atomic symbols. For example, the expression
stem:[-((3+x)-(z+5))] matches the pattern stem:[-(a-b)] and is rewritten as
stem:[(z+5)-(3+x)]. The transformation is visually represented here:

[.text-center]
[mermaid, format=png, align="center"]
....
---

  look: neo
---

        direction TB
        A((−)) --> B((−))
        B --> C((+))
        B --> D((+))
        C --> H((3))
        C --> I((x))
        D --> J((z))
        D --> K((5))
    end
    subgraph b [ ]
        direction TB
        E((−))
        E --> F((+))
        E --> G((+))
        F --> L((z))
        F --> M((5))
        G --> N((3))
        G --> O((x))
    end
    a --"Simplification"--> b
....

This simple example is representative of the larger design. Rules can match
subexpressions, rewrite them in a canonical form, and interact recursively so the
system can simplify deeply nested expressions. The same mechanism is used for
solving equations, evaluating derivatives, matrix manipulation, and circuit
transformations.

=== CAS rules overview

==== Introduction

_ASysC_ uses rules to perform a broad range of mathematical operations, including:

- simplification of expressions,
- solving first- and second-degree equations,
- solving systems,
- matrix operations,
- determinant calculations,
- Taylor series decompositions.

The same machinery is used to model circuits: Kirchhoff's laws, time-domain and
frequency-domain transforms, and linearization of nonlinear functions are all
implemented as symbolic rules.

The rule set includes multiple system-solving approaches:

* Gauss-Jordan elimination.
* Cramer's rule, also known as the determinant method.

Both methods have trade-offs. Cramer's method can preserve equation forms that
are useful for piecewise switch models, such as an ideal diode's zero-voltage or
zero-current states, but it is often slower than Gauss-Jordan elimination. The
best method depends on the structure of the system being transformed and the
desired symbolic properties of the result.

==== Rule definition files

The project organizes its symbolic behavior in a set of rule files that provide
both general algebraic operations and circuit-specific transformations:

[horizontal]
components.rule:: Definitions of analog components.
derivatives.rule:: Derivative transformations.
electricity.rule:: Kirchhoff's laws and time- and frequency-domain transforms.
evaluation.rule:: Evaluation of constant expressions.
ic.rule:: Higher-level integrated circuits, including the NE555 model.
includes.rule:: Default list of rule files loaded by the application.
logic.rule:: Logic gates and digital components such as D and SR flip-flops.
main.rule:: Core algebraic and simplification rules.
matrix_vector.rule:: Vector and matrix operations.
symbols.rule:: Operator and symbol definitions.
tests.rule:: Built-in regression checks.
units.rule:: Engineering suffixes such as `k`, `u`, and `n`.

These files use lowercase names. The `includes.rule` file determines which rules
are loaded by default, and a circuit can explicitly include additional rule files
when a design needs specialized behavior.

==== Structure of a rule

The following examples use the interactive console as a symbolic calculator.
After building the project, start the application from the repository root:

[source, console]
----
./bin/asysc
----

At the prompt, enter an expression:

[source, console]
----
> 2*2
4
----

Variables can be assigned symbolic expressions:

    > b:=a+a
    2*a
    > a:=2
    2
    > b
    4

Initially, stem:[b] stores the expression stem:[2a] without requiring a value
for stem:[a]. Assigning stem:[a := 2] then allows the system to evaluate
stem:[b] as stem:[4]. This symbolic manipulation is one of the main differences
between a CAS and an ordinary calculator.

In _ASysC_, rules and functions are defined with the assignment operator *:=*.

The next example defines a simple addition function:

    > my_sum(a,b) := a + b
    > my_sum(2,3)
    5

Rules can also match an expression tree. In the example below, `f` matches
expressions whose top-level operator is `+`, then replaces that expression with a
product:

    > f(a+b):=a*b
    a*b
    > f(2+4)
    8

This pattern-matching feature lets _ASysC_ transform expression trees by
recognizing a structure and replacing it with a new expression that preserves the
intended semantics.

[mermaid, format=png, align="center"]
....
---

        direction TB
        B((+))
        B --> C((a))

        E --> G((b))
    end

....

For routine mathematical work, the system already includes many built-in rules.

Example of derivative calculation with the *DER()* function:

    > DER(COS(3*x),x)
    -(3*SIN(3*x))

Example of writing a function as a Taylor sequence with the *TAYLOR()* function:

    > TAYLOR(COS(x),x,0,10)
    1-2.7557319224e-07*x^10+2.48015873016e-05*x^8-0.00138888888889*x^6+0.0416666666667*x^4-0.5*x^2

Example of solving equations with function *SOLVE()*:

    > SOLVE(x-2,x)
    2
    > SOLVE(x^2-2*x+4,x)
    {1-1.73205080757*j(),1+1.73205080757*j()}

Example of solving systems of equations:

    > SOLVE({x-y+1,x+y-5},{x,y})
    {2,3}

Another useful capability of _ASysC_ is its support for lists. Lists provide a
compact way to group related expressions and are used throughout circuit and
component definitions:

    > my_list := {a;b;c}

==== Recursions with rules

Rules can call themselves recursively. A recursive factorial definition is only
useful if it includes a terminating case. In the following example, the base case
stops the recursion once the argument reaches 1:

    > my_factorial( x ) := x * my_factorial( x - 1 )
    > my_factorial( 1 ) := 1 

Without the second rule, evaluation would not have a terminating case. With
both rules defined, evaluate the factorial:

    > my_factorial( 6 )
    720

The result is stem:[720], which is stem:[6!].

== Compilation, installation and use

=== Compilation and installation

Build the project from its root directory with GNU Make and a C++ compiler:

[source, console]
----
git clone https://github.com/analog-system-compiler/asysc.git
cd asysc
make -j4
----

The source and build configuration are in the repository root. The symbolic
expression engine is in `src/lib/`, the ASysC application in `src/app/`, and
component rules in `rules/`. The build also generates Python models for the
examples.

Install NumPy and Matplotlib in the Python environment used to run the
simulation scripts. A graphical Matplotlib backend is needed to display plots;
headless environments can use a non-interactive backend.

=== _ASysC_ command-line options

The file-compilation mode accepts these options:
    
[horizontal, labelwidth=4]    
-i:: Input circuit description (`.cir`).
-o:: Output Python file (`.py`). The default output name is `out`.
-t:: Analysis type: `ac` or `trans`.
-l:: Output language. `python` is the supported language.

For example, from the repository root:
[source, console]
----
./bin/asysc -i examples/ac/RLC_slider/RLC.cir \
  -o examples/ac/RLC_slider/RLC.py -t ac
----

This creates a Python model for AC analysis. The command-line compiler
recognizes the circuit definition named `CIRCUIT` by default.

=== Applying _ASysC_ to electronics

==== From equations to simulation

ASysC generates the circuit model, while Python performs the numerical
simulation. The examples use NumPy for numerical operations and Matplotlib for
plots, but users can use other Python libraries for post-processing and
visualization.

The workflow has four steps:

. Describe the circuit in a `.cir` netlist and define any required components
  in `.rule` files.
. Compile the netlist with ASysC to generate a Python circuit model.
. Run the generated model with a Python simulation script.
. Use Python libraries such as Matplotlib to inspect or plot the results.

This is illustrated below:

[mermaid,format=png, align="center"]
----
---

  theme: neutral

---

B("Generated Python model")
C("Simulation results")
A -- "Compile with ASysC" --> B -- "Run with Python" --> C
----

Generated model files are build outputs and may be overwritten when the netlist
is recompiled. Each example also uses:

[horizontal]
*circuit_base.py*:: Shared runtime classes used by generated circuit models.
*simulation.py*:: User-editable Python code that selects simulation settings,
  processes the results, and optionally plots them.

Simulation histories are exposed to Python and can be processed with NumPy.
For example, transient data can be analyzed further with a Fourier transform.

=== Declaring a component

In _ASysC_, a circuit rule returns a collection of component instances, and a
component rule returns its equations. The following template shows the
general form of a component definition:

----
my_component(node1, node2, ..., node_n, parameter1, ..., parameter_n) := {
    equation1;
    equation2
}
----

The following example defines a resistor `R1` connected between `node_p` and
`node_n`:

image::across_through.png[scale=50%,align="center"]

The resistor definition contains three equations:

* `ACROSS()` introduces the voltage between the two terminals.
* `THROUGH()` introduces the current through the component.
* Ohm's law relates them with stem:[U = R I].

This gives the following declaration for the resistor:

----
NAME.CR(node_p, node_n, R) := {

    NAME.U = ACROSS(node_p, node_n);
    NAME.I = THROUGH(node_p, node_n);
    NAME.U = R * NAME.I

};
----

The `ACROSS()` and `THROUGH()` quantities are analogous to the across and
through quantities used by VHDL-AMS. An inductor uses `DER()` to express its
voltage-current relation:

----
NAME.CL(node_p, node_n, L) := {

    NAME.U = ACROSS(node_p, node_n);
    NAME.I = THROUGH(node_p, node_n);
    NAME.U = L * DER(NAME.I, t)

};
----

The capacitor declaration uses the corresponding current-voltage relation:

----
NAME.CC(node_p, node_n, C) := {

    NAME.U = ACROSS(node_p, node_n);
    NAME.I = THROUGH(node_p, node_n);
    NAME.I = C * DER(NAME.U, t)

};
----

The dot in an instance such as `R1.CR(...)` is the hierarchical operator. It
prefixes internal quantities with the instance name, avoiding name collisions
when the component equations are combined into a circuit.

Thus, `NAME` is replaced by `R1`: the internal quantities `NAME.U` and
`NAME.I` become `R1.U` and `R1.I`.

[NOTE]
====
1. Prefixing nodes with `@` is optional; it can make terminal parameters
   easier to recognize. Descriptive node names are also valid.

2. Semicolons separate entries inside a `{ ... }` list. Do not put a
   semicolon after the final entry.
====


=== Instantiating a component

A component instantiation is written in the following form:

    <Instance name>.<Component name>( <node list>, <parameter list>)

For example, a resistor named `R1`, connected between nodes `@3` and `@4`
with resistance `1K`, is instantiated as follows:
    
    R1.CR( @3, @4, 1K)

=== Quantities

_ASysC_ supports engineering suffixes for expressing component values:

[horizontal]
p:: pico (`10^-12`)
n:: nano (`10^-9`)
u:: micro (`10^-6`)
m:: milli (`10^-3`)
k or K:: kilo (`10^3`)
M:: mega (`10^6`)
G:: giga (`10^9`)

For example, `1G` represents `1000000000`.
